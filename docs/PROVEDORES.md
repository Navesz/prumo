Separado disso: o JSON de entrada/saída fica retido 30 dias por padrão (header X-Fal-Store-IO, default 1, 0 desliga). Atenção: a doc de webhooks diz que o RESULTADO na fila é retido ~1 hora após a conclusão, e só ~6 MINUTOS quando o payload tem ≥10 KB.

**Armadilhas.**

1. O corpo HTTP é PLANO. O {"input": {...}} que aparece em snippets de terceiros é assinatura de SDK, não do HTTP — mandar wrapper dá erro de schema. 2) Monte as URLs de status/resultado a partir de status_url/response_url devolvidos no submit; a doc mostra tanto GET .../requests/{id} quanto .../response, não vale hardcodar. 3) RETENÇÃO CURTA DO RESULTADO: ~1h, e ~6 min se o payload ≥10 KB (doc de webhooks). Em fan-out com fila cheia, um worker lento perde o resultado de uma imagem JÁ PAGA. Buscar e persistir na hora. 4) Retry automático é ligado por padrão: em falha a fal reexecuta. A doc de publicação de modelos diz que 5xx não é cobrado, mas isso é a visão do AUTOR do modelo; para o CONSUMIDOR não achei garantia equivalente — NÃO VERIFICADO, então use X-Fal-No-Retry: 1 quando o teto de gasto importar. 5) X-Fal-Billable-Units devolve UNIDADES, não dólares; a conversão depende do unit_price do endpoint. USD real só em GET /v1/models/billing-events (campos output_units, unit_price, percent_discount, cost_subtotal, cost_discount, cost_total, cost_estimate_nano_usd, filtro por request_id, janela máx. 90 dias, cursor). O ATRASO até o evento aparecer NÃO está documentado — NÃO VERIFICADO. 6) Não confirmei se o header X-Fal-Billable-Units aparece no GET do resultado da fila ou só na chamada síncrona fal.run — NÃO VERIFICADO; teste antes de basear o ledger nele. 7) Mídia gerada é pública por URL por padrão (link não-listado). Galeria "privada" exige File ACL / initial_acl ou reingestão para storage próprio. 8) Expiração padrão do CDN não documentada: trate TODA URL como efêmera. 9) Concorrência 2 numa conta nova destrói a promessa de fan-out simultâneo — a UI precisa mostrar queue_position, não fingir paralelismo. 10) Sub-endpoints (/inpainting, /image-to-image) têm SCHEMA DIFERENTE do endpoint base: não dá para assumir um schema único por família de modelo; o índice de modelos do Prumo precisa guardar schema por endpoint_id. 11) sync_mode=true (data URI) apaga o output do histórico — bom para privacidade, péssimo para auditoria/ledger. 12) Webhook: NÃO segue redirects (3xx = falha permanente), até 31 tentativas, timeout de 15s na primeira entrega e 120s nas retentativas, assinatura ED25519 (headers X-Fal-Webhook-Request-Id / -User-Id / -Timestamp / -Signature) verificada contra JWKS em https://rest.fal.ai/.well-known/jwks.json (cache até 24h) — handler tem que ser idempotente por request_id. 13) CORS: a doc oficial NUNCA promete CORS; a evidência é o README do fal-js dizendo que o cliente "is designed to work in any JS environment, including directly in your browser". Não consegui validar o preflight empiricamente (rede bloqueada no sandbox) — NÃO VERIFICADO. E mesmo que passe, a fal recomenda explicitamente proxy (createRouteHandler / header x-fal-target-url), o que para o Prumo é obrigatório de qualquer jeito porque a chave é do USUÁRIO.

**Armadilhas.**

1. A JANELA DE 1 HORA É O MAIOR RISCO: URL de saída expira em 1h E o registro (input, output, logs) é apagado em 1h por padrão. Sem ingestão imediata para storage próprio (R2/S3), o Prumo perde a imagem que o usuário pagou. 2) A resposta NÃO traz custo. Só metrics.predict_time e metrics.total_time. Para virar dinheiro você precisa saber o HARDWARE em que rodou e o preço/segundo dele — e o objeto prediction não devolve o hardware de forma documentada (NÃO VERIFICADO). Modelos oficiais são cobrados por unidade de saída (por imagem/token), regra diferente da de tempo. Conclusão dura: o teto de gasto do Prumo na Replicate é ESTIMATIVA local, não conciliação — não existe endpoint de billing/usage documentado. 3) CORS bloqueado: chamada direta do browser falha com "No 'Access-Control-Allow-Origin' header is present" (issue replicate/replicate-javascript#164, 29/11/2023, e stackblitz/bolt.new#2254). Proxy de servidor é OBRIGATÓRIO. Ressalva: isso é evidência de issue, a doc oficial simplesmente não fala de CORS — NÃO VERIFICADO por preflight (rede bloqueada neste sandbox). 4) Dois shapes de request no mesmo provedor: comunidade exige "version" (hash de 64 chars) no corpo; oficiais usam o path /v1/models/{owner}/{name}/predictions sem version. O adaptador precisa dos dois caminhos. 5) Versão pinada pode ser removida/despublicada pelo autor → chamada quebra depois de meses. O índice do Prumo tem que guardar o hash E revalidar. 6) Prefer: wait é no MÁXIMO 60s e pode devolver "starting" mesmo assim — o mesmo code path tem que aceitar resposta pronta OU incompleta. Nunca trate wait como garantia de síncrono. 7) Cold boot: modelo da comunidade pouco usado leva minutos subindo, e predict_time NÃO inclui essa espera — a UX precisa distinguir "starting" de "processing", senão parece travado. 8) Rate limit degrada com saldo baixo (até 6 rpm): um fan-out de 8 modelos pode tomar 429 em massa numa conta quase zerada. Backoff obrigatório. 9) Webhook: HMAC-SHA256 (padrão Standard Webhooks) com headers webhook-id, webhook-timestamp, webhook-signature; o segredo é ÚNICO DA CONTA (GET /v1/webhooks/default/secret, prefixo whsec_) — não há segredo por endpoint, e comparação tem que ser em tempo constante. webhook-id repete nas retentativas → idempotência obrigatória. 10) Cancelar não devolve o que já foi computado; se a cobrança do tempo já gasto continua NÃO está documentado — NÃO VERIFICADO. 11) Saída como FileOutput nas libs ≥1.0.0 (não string de URL); em JS precisa useFileOutput:false para voltar a receber URL. Isso quebra código antigo silenciosamente.

## Contrato comum de adaptador

- CONTRATO ÚNICO DE ADAPTADOR (cobre fal.ai e Replicate e já acomoda KIE/WaveSpeed/Runware/OpenAI/Google)

O denominador comum real é: **os dois são "job assíncrono com resultado efêmero, custo não confiável na resposta e chave que nunca pode ir ao browser"**. Todo o resto é tradução. Logo o adaptador NÃO deve ser "cliente HTTP por provedor", e sim uma máquina de estados de JOB.

1. `describe(): ProviderCapabilities`
   { id, authHeaderBuilder, supportsSyncFast, supportsWebhook, supportsCancel, costInResponse: 'none'|'units'|'usd', outputDelivery: 'ephemeral-url'|'data-uri', outputTtlSeconds|null, corsFromBrowser: boolean, concurrencyModel: 'slots'|'rpm', limits }
   Isso mata o if/else espalhado: a UI e o orquestrador leem capacidades, não nomes de provedor.

2. `resolveModel(ref: PrumoModelRef): ProviderModelRef`
   Precisa suportar as DUAS formas de identidade que existem no mundo real: id-no-path (fal: `fal-ai/flux-lora/inpainting`) e owner/name+versionHash (Replicate). O registro do Prumo guarda `{provider, endpointId, versionPin|null, schemaHash, capabilities[]}`. Sub-endpoint com schema próprio é um MODELO diferente no índice — não uma flag.

3. `buildRequest(canonical: GenSpec): HttpRequest`
   GenSpec canônico: { prompt, negativePrompt?, task: t2i|i2i|inpaint|upscale|edit, initImage?, mask?, refImages[]?, size{w,h}|preset, n, seed?, steps?, guidance?, loras[]?, outputFormat, safety }.
   O adaptador é quem sabe que fal manda **corpo plano** e Replicate manda **{version, input:{...}}**, que fal usa `image_size` e Replicate usa `aspect_ratio`/`width`, que LoRA na fal é `loras[{path,scale}]` em runtime e na Replicate é uma **versão treinada** (então `loras` vira `resolveModel` de outra versão, não um campo). Feature não suportada não é silenciada: devolve `UnsupportedFeature`, e o fan-out remove o modelo da rota antes de gastar.

4. `submit(req, {idempotencyKey}) -> Job { providerJobId, mode, pollUrl?, cancelUrl?, submittedAt, reservedCostUsd }`
   Sempre pela via de FILA (queue.fal.run / POST /v1/predictions sem Prefer). O caminho rápido (`fal.run` direto / `Prefer: wait=N`) é uma OTIMIZAÇÃO opcional que **precisa cair no mesmo Job** quando não termina a tempo — Replicate devolve `starting` depois de 60s, então o retorno de `submit` é sempre um Job, nunca um resultado.

5. `poll(job) -> JobState { state: queued|running|succeeded|failed|canceled, queuePosition?, logs?, raw }`
   Normaliza IN_QUEUE/IN_PROGRESS/COMPLETED (fal) e starting/processing/succeeded/failed/canceled (Replicate). `queuePosition` existe na fal e não na Replicate: campo opcional, UI degrada.

6. `fetchResult(job) -> Result { assets: [{url, dataUri?, mime, width, height, expiresAt}], seed?, safetyFlags?, providerRaw }`
   **Invariante do Prumo, não do provedor: nada é considerado entregue até estar no storage próprio.** Os dois expiram (Replicate: 1h documentado e o registro inteiro some; fal: expiração configurável, default não documentado, e o resultado na fila cai para ~6 min quando o payload ≥10 KB). O pipeline é submit → poll → fetch → **ingest imediato** → só então marcar `succeeded` na galeria.

7. `verifyWebhook(headers, rawBody) -> {ok, jobId}`
   Duas criptografias diferentes atrás de uma assinatura só: ED25519 + JWKS (fal) e HMAC-SHA256 estilo Standard Webhooks com `whsec_` (Replicate). Handler idempotente por `providerJobId` nos dois casos (fal reentrega até 31x e não segue redirect; Replicate repete o mesmo `webhook-id`).

8. `usage(job) -> Cost { costUsd?, units?, computeSeconds?, source: 'exact'|'derived'|'estimated', settledAt? }`
   É AQUI que o Prumo se diferencia, e é aqui que os dois provedores divergem de forma incontornável — o contrato tem que expor a divergência em vez de esconder:
   - fal → `units` no header `X-Fal-Billable-Units` (unidade, não dinheiro) e USD **exato** depois, por `request_id`, em `GET /v1/models/billing-events` (`cost_total`). Fonte 'exact' na conciliação.
   - Replicate → **nada**. Só `metrics.predict_time`. Fonte 'derived' via tabela local de preço (hardware×s ou por-imagem nos modelos oficiais), e sem API de billing para conferir.
     Consequência de produto: o ledger tem TRÊS estados — `estimated` (pré-voo, com `POST /v1/models/pricing/estimate` na fal e tabela local na Replicate), `derived` (na conclusão) e `settled` (só onde o provedor reconcilia). O teto de gasto por sessão/mês tem que ser **aplicado no submit, contra `estimated`**, porque em pelo menos um dos dois provedores o número real nunca chega.

9. `estimate(modelRef, spec) -> {costUsd, confidence}` — obrigatório para o "mostra o custo ANTES de gastar". fal tem endpoint oficial; Replicate é estimativa local. `confidence` vai para a UI, não some.

10. `mapError(httpStatus, body, headers) -> PrumoError`
    Taxonomia única: `auth_invalid` (401 fal / 401 Replicate), `scope` (403 fal), `rate_limited` (429 concurrent_requests_limit + X-Fal-needs-retry na fal; 429 "Request was throttled" na Replicate, que APERTA com saldo baixo até 6 rpm), `timeout` (504 start_timeout), `model_gone` (versão despublicada na Replicate), `unsupported_input`, `content_blocked`, `provider_down`. Backoff e circuit breaker vivem no orquestrador, não no adaptador.

REGRAS QUE O CONTRATO IMPÕE AO PRUMO (consequência direta do que foi verificado):

- Adaptador roda **só no servidor**. Replicate bloqueia CORS na prática; fal talvez permita mas a chave é do USUÁRIO e não pode transitar no bundle. O front nunca fala com provedor — fala com o Prumo.
- A chave do usuário é credencial de terceiro guardada por você: cifrada em repouso, nunca logada, nunca em query string, e o adaptador recebe um handle, não a string.
- Fan-out é limitado por `concurrencyModel`: na fal uma conta nova tem **2 slots** — disparar 8 modelos "ao mesmo tempo" enfileira 6. A UI tem que mostrar posição real na fila, senão a promessa central do produto vira mentira visível.
- Retry automático é um risco de custo (fal reexecuta por padrão). Quando o teto de gasto estiver perto, mandar `X-Fal-No-Retry: 1`.
- O que este contrato NÃO resolve: catálogo e preço por modelo mudam fora do código; `schemaHash` por endpoint e revalidação periódica do `versionPin` são serviço à parte, não responsabilidade do adaptador.

- CONTRATO ÚNICO DE ADAPTADOR — o que os três (e também fal.ai/Replicate) cabem dentro.

O denominador comum real é pequeno e honesto: **todos são Bearer, todos são assíncronos por baixo, todos devolvem URL que morre, e nenhum concorda sobre custo.** O contrato tem que ser desenhado a partir dessas quatro verdades, não a partir do provedor mais bonito.

```ts

  capabilities: Capabilities

    expiresAt: Date
    seed?: string | number
  }>
```

**As sete decisões que o contrato é obrigado a impor** (cada uma nasce de uma diferença concreta medida acima):

1. **Assíncrono é o caso base, síncrono é otimização.** Nenhum dos três é síncrono por padrão. `submit -> providerJobId -> poll/webhook` é o único fluxo que serve para os três. `enable_sync_mode` (WaveSpeed) e `deliveryMethod:"sync"` (Runware) entram como atalho opcional, nunca como premissa de design.

2. **Duas identidades por job, sempre.** `clientJobId` (UUID v4 do Prumo) e `providerJobId`. Na Runware eles coincidem (o `taskUUID` é gerado pelo cliente); na KIE e na WaveSpeed o id é do servidor. Isso dá idempotência de graça na Runware e obriga chave de idempotência própria nos outros dois — o que é essencial porque a WaveSpeed avisa que **retry cego de POST cobra duas vezes**.

3. **`persistAssets()` roda ANTES de marcar o job como concluído.** Prazos medidos: Runware 7 dias (configurável via `ttl`), WaveSpeed 7 dias, KIE entre 20 minutos e 24 horas dependendo de qual página da própria doc você lê. Galeria e histórico do Prumo não podem apontar para URL de provedor — copiar para storage próprio faz parte do contrato, não é otimização posterior.

4. **Custo é um objeto de três campos, nunca um número.** Runware devolve `cost` em USD exato na resposta (`includeCost:true`, sempre ligado). WaveSpeed devolve USD **antes** (`/model/price`) e nada depois. KIE devolve `creditsConsumed` **depois**, em créditos, sem conversão oficial. Por isso o ledger precisa de `{usd?, creditos?, confianca}` e a UI precisa distinguir "custou $0,0013" de "estimado $0,045" de "3 créditos ≈ $0,015 (derivado)". Colapsar isso em um float é como o teto de gasto vira mentira.

5. **`partial` é um estado de primeira classe.** A Runware manda `data[]` e `errors[]` na mesma resposta de um array de tarefas. E o próprio fan-out do Prumo é parcial por natureza: 6 modelos disparados, 4 voltam. Um enum `succeeded|failed` binário perde imagem e erra cobrança.

6. **O escalonador de fan-out respeita orçamento por provedor.** WaveSpeed Bronze = **2 simultâneas e 5 predictions/min**; KIE = 20 requisições/10s com 429 que **não enfileira**; Runware = sem teto fixo mas recomendando 2–4 simultâneas. Sem `concurrencyBudget()` no adaptador, o recurso principal do Prumo (um prompt em vários modelos) vira uma máquina de gerar 429 na conta nova de WaveSpeed.

7. **Um só endpoint de webhook, autenticado por segredo na URL.** `POST /webhooks/:provider/:clientJobId?token=<segredo-por-job>`. É o menor denominador: a WaveSpeed registra webhook como **query param** na URL de submissão, a KIE como campo `callBackUrl` no body, a Runware como `webhookURL` por tarefa — e a Runware **não oferece verificação de assinatura**, só parâmetro de URL. Logo o segredo tem que estar na URL e o corpo nunca pode ser confiado sozinho; deduplicar por `clientJobId`.

**O que NÃO cabe no contrato comum** (e por isso vira campo `providerSpecific`, com o front escondendo o que o provedor não tem): `ttl` de saída (só Runware), preço pré-voo (só WaveSpeed), `strength`/`num_inference_steps`/`guidance_scale` (existem na KIE só em modelos abertos como qwen, e na Runware quase sempre, e quase nunca nos modelos fechados), ControlNet/LoRA/IP-Adapter (só Runware), e o id do modelo — que é **path** na WaveSpeed, **string sem regra** na KIE e **AIR versionado** (`bfl:6@1`) na Runware. Não existe id de modelo derivável: o índice vivo de preço do Prumo tem que ser também um índice de tradução de ids, mantido à mão e versionado.

**E o que não funciona:** browser falando direto com provedor. Só a WaveSpeed tem CORS aberto (medido por mim em 2026-08-24: `Access-Control-Allow-Origin: *`), a KIE não documenta e manda explicitamente não expor chave no frontend, e a Runware só é "amigável a browser" via WebSocket — que ignora CORS mas exigiria a chave do usuário no cliente. Como as chaves são do usuário e ficam no banco do Prumo, **todo tráfego passa pelo backend, sem exceção**; o campo `browserDirect` no adaptador é informativo e não deve alterar rota nenhuma.

- CONCLUSAO DE ARQUITETURA ANTES DO CONTRATO: os tres bloqueiam CORS. Nenhum deles pode ser chamado do navegador com a chave do usuario. Isso confirma tecnicamente o pedido do Leonardo ("BANCO DE DADOS, FRONTEND", plataforma real): o fan-out do Prumo TEM que rodar em worker no servidor, com as chaves guardadas cifradas no banco. Qualquer desenho local-first/browser-direct esta descartado por CORS, nao por preferencia.

CONTRATO UNICO — ImageAdapter. Sete membros cobrem OpenAI, Google e BFL sem vazamento de detalhe do provedor:

1. describe(): ModelCard[] — capacidades declaradas, nao inferidas. Campos: id, provider, modalidades (t2i, edit, mask, outpaint, upscale), maxRefImages (OpenAI: varias; Google: 14; BFL: 8), hasRealMask (OpenAI sim via canal alfa, BFL sim via /flux-pro-1.0-fill, Google NAO — inpaint so por instrucao textual), aspectRatios[], sizes[], outputFormats[], supportsSeed (BFL sim, OpenAI/Google nao), watermark ('synthid' | 'none' | 'unknown'), needsAccountVerification (true so na OpenAI). O frontend renderiza controles a partir daqui; nada de if(provider==='bfl') na UI.

2. authHeaders(key) -> Record<string,string> — unica diferenca real de autenticacao: {Authorization:`Bearer ${k}`} | {'x-goog-api-key':k} | {'x-key':k}. Regra transversal: chave NUNCA em query string, mesmo onde o provedor permite (Google).

3. estimateCost(req) -> {min, max, currency:'USD', basis:'table'|'tokens'|'megapixel', confidence} — obrigatorio ANTES de submeter, porque e isso que alimenta o teto de sessao/mes. As tres bases sao diferentes e o campo basis existe justamente para isso: Google e tabela deterministica (modelo x resolucao), OpenAI e token de saida por quality x size convertido pelo indice, BFL e por megapixel com preco base do primeiro MP.

4. submit(req, key) -> Job, onde Job = {state:'done', assets:AssetRef[], usage} | {state:'pending', handle:string, expiresAt?:Date}. AQUI ESTA A UNIFICACAO PRINCIPAL: OpenAI e Google sao sincronos e devolvem 'done' na hora; BFL devolve 'pending' com handle = polling_url INTEIRO (nunca reconstruido). Tudo entra na mesma fila do Prumo, e o job sincrono simplesmente pula a fase de poll. Nao criar dois caminhos de codigo.

5. poll(handle, key) -> Job — implementado so pela BFL; no-op nos outros.

6. materialize(assets, key) -> Bytes[] — a operacao que os tres formatos de saida obrigam a existir. AssetRef e {kind:'inline', b64} (OpenAI b64_json, Google output_image.data / inlineData.data) ou {kind:'url', href, ttlSeconds:600} (BFL delivery.*.bfl.ai). REGRA DE OURO DO WORKER: persistir em storage proprio (R2/S3) e so entao marcar o job como concluido no banco. Motivo concreto: a URL da BFL expira em 10 minutos, e o base64 da OpenAI ocupa memoria do worker (imagem 4K pode passar de 10 MB), entao os dois extremos exigem a mesma disciplina — nunca deixar o binario so na resposta do provedor.

7. normalizeResult(raw) -> {usage, settledCost?, terminalState} com terminalState em {OK, MODERATED, RATE_LIMITED, NO_CREDIT, AUTH_FAILED, ACCOUNT_UNVERIFIED, PROVIDER_ERROR}. MODERATED precisa ser estado proprio e NAO retentavel: a BFL o entrega como HTTP 200 com status 'Request Moderated'/'Content Moderated', a OpenAI como error.code='moderation_blocked' + moderation_details, o Google via filtro de seguranca. ACCOUNT_UNVERIFIED existe so por causa da verificacao de organizacao da OpenAI, que produz 403 com chave valida — sem esse estado o Prumo vai dizer "chave invalida" para o usuario e ele vai passar horas debugando a coisa errada.

RECONCILIACAO DE CUSTO — os tres reportam de forma incompativel, entao o ledger precisa de dois campos separados, estimated e settled:

- BFL: settled REAL em creditos (1 credito = $0,01), mas so no SettledCostResultResponse; alem disso devolve input_mp/output_mp para auditar o preco por megapixel. Unico dos tres que fecha a conta sozinho.
- OpenAI: devolve usage {total_tokens, input_tokens, output_tokens, input_tokens_details{text_tokens, image_tokens}} — tokens, nao dolares. O indice de precos do Prumo converte (image output entre $8 e $40 por 1M de tokens conforme o modelo).
- Google: nao devolve dolar; o preco e tabelado por modelo x resolucao ($0,0336 a $0,24 por imagem). Deterministico, mas 100% dependente do indice estar atualizado.
  Consequencia de produto: o teto de gasto do Prumo trava pelo estimated (pre-gasto) e o ledger corrige pelo settled quando ele existir. So a BFL fecha a conta sozinha; nos outros dois, o indice de precos e a fonte de verdade — e por isso o item 3 do escopo (indice vivo de preco) nao e um extra, e uma dependencia de correcao do item 2 (teto de gasto).

O QUE O CONTRATO NAO CONSEGUE ESCONDER (dizer isso na UI, nao no codigo): mascara de inpainting nao existe no Google; seed nao existe em OpenAI nem Google; SynthID e obrigatorio e irremovivel em toda imagem do Google; e a OpenAI exige verificacao com documento e reconhecimento facial antes da primeira imagem. Esses quatro pontos mudam a escolha do usuario e devem aparecer no ModelCard do item 1, nunca serem simulados pelo adaptador.

- CONTRATO ÚNICO DE ADAPTADOR — "ImageProviderAdapter" (cobre os 5, mas o Fireworks entra só como stub morto)

Antes do contrato, os 5 fatos que ele precisa absorver (todos verificados, ver campo `fontes` de cada provedor):

(1) AUTH tem só DUAS formas: `Authorization: Bearer <k>` (Together, Novita, DeepInfra, Fireworks) e `x-api-key: <k>` (Segmind). NÃO é uma variação livre — é um enum de 2 valores.
(2) MODO tem só DUAS formas: sync (Together, DeepInfra, Fireworks, Segmind v1) e submit+poll (Novita v3, Segmind v2). Nenhum dos cinco tem webhook documentado para imagem.
(3) SAÍDA tem QUATRO formas: JSON com url (Together default, Novita), JSON com b64 (Together `response_format:"base64"`, DeepInfra — que só aceita b64_json), bytes binários no corpo (Fireworks com `Accept: image/jpeg`, Segmind v1/v2 default). TODA url expira (Novita expõe `image_url_ttl:3600`; Segmind v2 retém 1h; Together não documenta TTL e o CDN dá 403 com User-Agent vazio).
(4) CUSTO NA RESPOSTA: NENHUM dos cinco devolve custo/usage no corpo da geração de imagem. Zero. O ledger do Prumo NÃO pode depender do provedor.
(5) CORS: os cinco devolvem `Access-Control-Allow-Origin: *` no preflight (sondado 2026-08-24). Isso NÃO muda a arquitetura — o Prumo tem que chamar pelo backend mesmo, senão não há teto de gasto, nem ledger, nem persistência. CORS liberado serve só como plano B de preview.

--- CONTRATO ---

interface ImageProviderAdapter {
id: 'together' | 'novita' | 'deepinfra' | 'fireworks' | 'segmind'

// 1. AUTH — enum de 2, nunca string livre
auth(key: string): Record<string,string>
// together|novita|deepinfra|fireworks -> { Authorization: `Bearer ${key}` }
// segmind -> { 'x-api-key': key }
// REGRA DURA: o núcleo NUNCA injeta headers de auth globais. Se o Segmind
// receber Authorization + x-api-key juntos, ele responde 401
// {"error":"Both Authorizationn and x-api-key can not be present"} (sic, com o typo).

// 2. REQUEST — o núcleo fala UMA linguagem; o adaptador traduz
buildRequest(job: ImageJob): { url: string, method: 'POST', headers: Record<string,string>,
body: JsonBody | FormDataBody, accept: 'json' | 'bytes' }
// Tradução de geometria (aqui mora 80% da divergência):
// together : width/height em px (Schnell/Kontext usam aspect_ratio)
// deepinfra: size:"WxH"
// novita : size:"W*H" (ASTERISCO, não "x")
// segmind : img_width/img_height (SDXL) ou aspect_ratio (imagen-4) — por modelo
// Tradução de saída:
// together : response_format:"base64" | "url" (NÃO é "b64_json" como na OpenAI)
// deepinfra: response_format:"b64_json" (único valor aceito)
// fireworks: header Accept: image/jpeg
// segmind : campo booleano base64 no corpo

// 3. SUBMIT — sempre devolve um handle, mesmo quando é sync
submit(job: ImageJob): Promise<JobHandle>
// JobHandle = { mode:'sync', result: ImageResult }
// | { mode:'poll', jobId: string, pollUrl: string, firstPollAfterMs: number }
// Isso elimina o if/else do núcleo: o worker sempre faz submit -> (poll)* -> settle.

// 4. POLL — no-op para os sync
poll(handle: JobHandle): Promise<'queued'|'running'|'succeeded'|'failed'>
// novita : GET /v3/async/task-result?task_id= -> TASK_STATUS_{QUEUED,PROCESSING,SUCCEED,FAILED}
// segmind: GET /v2/requests/{id}/status -> QUEUED|PROCESSING|COMPLETED|FAILED

// 5. MATERIALIZE — obrigatório, não opcional
materialize(handle: JobHandle): Promise<Array<{ bytes: Buffer, mime: string }>>
// Contrato: o adaptador SEMPRE entrega bytes. Se o provedor deu url, o adaptador
// baixa AGORA (com User-Agent não-vazio, senão o CDN da Together dá 403) e o núcleo
// grava no storage do Prumo (R2/S3). Nunca guardar url de provedor no banco:
// Novita expira em 3600s, Segmind v2 em 1h, Together não diz — logo, assume-se curto.

// 6. PRICE — a peça mais importante do Prumo, e é 100% local
price(job: ImageJob): { usd: number, formula: string, source: 'catalog', asOf: Date }
// Assinatura obrigatória: price(width, height, steps, n), NÃO um float por imagem.
// Motivo concreto: Together FLUX1.1[pro] e Kontext[pro] são $/megapixel; DeepInfra
  //   FLUX-1-dev é "$0.009 x (w/1024) x (h/1024) x (iters/25)". Um catálogo de
// "preço por imagem" mente nesses casos. O índice vivo de preço do Prumo precisa
// guardar uma EXPRESSÃO, não um número.
// Como nenhum dos 5 devolve custo, o ledger grava sempre source:'catalog_estimate'
// e o teto de gasto é pré-autorizado (reserva antes do submit, baixa no settle).

// 7. ERRORS — normalizar, porque cada um inventa o seu
mapError(status: number, body: unknown): { kind: 'auth'|'rate_limit'|'invalid_request'
|'content_blocked'|'expired'|'provider', retryable: boolean }
// auth: together 401 invalid_api_key | deepinfra 401 detail | segmind 401 error
// novita 403 INVALID_API_KEY no /v3 mas 401 FAILED_TO_AUTH no /openai (o mesmo
// provedor usa DOIS códigos diferentes para a mesma falha)
// rate_limit: 429 em todos; só Together documenta header de retry (x-ratelimit-reset)
// expired: segmind 404 em request_id vencido; segmind 422 = job falhou (corpo tem o detalhe)
// content_blocked: segmind entrega bloqueio de conteúdo como FAILED, não como estado próprio
}

--- O QUE ISSO SIGNIFICA NA PRÁTICA PARA O PRUMO ---

- UM adaptador OpenAI-compatível resolve DOIS de verdade: DeepInfra (compatibilidade real e completa:
  /v1/openai/images/generations + /images/edits + /images/variations, com `size`, `n`, `b64_json`) e
  Together AI (mesmo path /v1/images/generations, mesmo Bearer, mas corpo divergente: width/height
  em vez de size, response_format:"base64" em vez de "b64_json"). Dá para usar a MESMA classe base
  com um mapper de 15 linhas para a Together. NÃO dá para apontar o SDK oficial da OpenAI para a
  Together e esperar que funcione.
- Novita e Segmind exigem adaptadores próprios de verdade (Novita por ser fila v3 com `size:"W*H"`;
  Segmind por ser rota-por-modelo com x-api-key e resposta binária). Mas ambos encaixam no MESMO
  contrato acima sem nenhuma exceção — é só preencher os 7 métodos.
- Fireworks NÃO deve entrar na v1 do Prumo. Geração de imagem foi declarada deprecada no changelog
  oficial em 2026-06-10 e as páginas de modelo de imagem já retornam "Model not found".
